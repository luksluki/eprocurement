## What

- **`services/procurement/requisition/store.go`** (new) — the persistence layer on top of the untouched #28 domain: `Create` (server-generated `PR-%06d` number + server-computed total), `Get`, `UpdateItems` (draft-only basket replace), `Submit` (draft → submitted with optional idempotency key). All queries run through `tenant.WithTenant` (RLS-scoped); edit/submit load the row `FOR UPDATE` and mutate under a `status = 'draft'` guard, so a concurrent edit/submit pair on one requisition serializes. IO sentinels live here (`requisition_not_found`, `requisition_forbidden`, `requisition_id_invalid`, `requisition_idempotency_key_invalid`, `requisition_idempotency_key_conflict`) — same package as the domain, whose file is unchanged.
- **Migration `0004_requisition_numbering_idempotency.sql`** — `procurement.requisition_counters (tenant_id PK, last_number)` with the 0001/0003 RLS pattern; `requisitions.submit_idempotency_key` + partial unique index `requisitions_tenant_submit_key_uidx (tenant_id, submit_idempotency_key) WHERE ... IS NOT NULL`.
- **proto `procurement.v1`** — `CreateRequisition` / `UpdateRequisition` / `SubmitRequisition` RPCs and the `Requisition` / `RequisitionItem` messages; `gen/go` regenerated (`make gen-proto`) and committed.
- **procurement server** — the three gRPC methods (`services/procurement/server/api.go`): currency normalized (trim + uppercase) at the boundary, items converted, ownership enforced, `mapRequisitionError` extended (NotFound / AlreadyExists / PermissionDenied / new InvalidArgument arms; `Aborted` for illegal transitions). `server.New` takes the requisition store; `methodPermissions` maps all three methods to `requisition:write`; `cmd/procurement/main.go` wires the store.
- **gateway** — `services/gateway/server/requisitions.go` (new): `POST /api/v1/requisitions`, `PUT /api/v1/requisitions/{id}`, `POST /api/v1/requisitions/{id}/submit` behind `RequirePermission(rbac.RequisitionWrite)` with edge normalization (currency trim+uppercase, item trim, `Idempotency-Key` 1–64 chars). `server.go` widens `WithProcurement` to the combined `ProcurementClient` interface (5 vendor + 3 requisition methods) and registers the routes in the same `if o.procurement != nil` block; `cmd/gateway/main.go` is unchanged (the generated client satisfies the wider interface). `vendorError` was refactored into a shared `grpcHTTPError` with the new `Aborted` → HTTP 409 arm; requisitions use it with their own message table.
- **Docs** — `docs/schema/procurement.md` (0004 section, requisition lifecycle, error-code tables, stale "persistence arrives with #29" note removed) and `docs/rbac.md` (ownership rule marked landed).

## Decisions

- **Ownership on edit/submit is enforced now — maintainer decision 2026-10-23** (escalated before implementation; the plan shipped without it). `docs/rbac.md` promised "a requester edits *their own* requisition" as a domain check arriving with the procurement services, and #29 is exactly that endpoint set. Rule: caller (`x-user-id`) must equal `requester_id`; `admin` is exempt; violations → `codes.PermissionDenied` → HTTP 403 with machine code `requisition_forbidden`. The check runs in the service layer (`api.go`) on an unlocked `Get` before the mutating call — `requester_id` is immutable, so there is no time-of-check/time-of-use gap, and the store stays free of role knowledge.
- **One idempotency key names one submit per tenant** (explicit): the partial unique index makes reuse across requisitions a 23505 → `requisition_idempotency_key_conflict` → 409. **Replay semantics pinned**: a replay of the same key returns the requisition's current state as-is (no second transition, no 409), whatever the status — today that can only be `submitted`; when #30/#31 add approve/reject, the same rule answers the "replay after approved" question without re-litigating. The replay check runs *after* the `FOR UPDATE` load, so replays are deterministic against racing writers. The key is recorded in the same transaction as the transition.
- **Number generation** — lazy init (`INSERT … SELECT coalesce(max(substring(number FROM 4)::bigint), 0) … ON CONFLICT DO NOTHING`, guarded by `number ~ '^PR-[0-9]+$'`) + `UPDATE … last_number + 1 RETURNING` inside the create transaction. Concurrent creators serialize on the counter row; failed creates roll the increment back (no gaps). Once a counter exists it is authoritative — later out-of-band rows do not move it. Demonstrated by a parallel test (8 goroutines → one gap-free consecutive run), addressing the review note that the "race-free" claim previously had no test.
- **GRANT rationale corrected** (review note): migration 0001's `ALTER DEFAULT PRIVILEGES … GRANT … ON TABLES TO eproc_app` already covers tables created later by the migrating role, so "without the GRANT the counter INSERT fails at runtime" would *not* be true in the standard setup. The explicit `GRANT SELECT, INSERT, UPDATE` on the counters is belt-and-braces following the 0003 pattern, nothing stronger.
- **Non-UUID `{id}` fails fast** (review note): `uuid.Parse` at the store → `requisition_id_invalid` → 400, instead of a 22P02 cast error surfacing as 502 "procurement unavailable". This follows the documents-store pattern; vendor still behaves the old way (noted, unchanged — out of scope).
- **Sentinel placement deviates from vendor deliberately**: the plan put the new IO sentinels in `store.go` (one package with the domain) so `requisition.go` stays byte-identical to #28; vendor keeps its sentinels in the domain file. Both packages' machine codes flow through `err.Error()` verbatim — store wrapping (`requisition: <what>: …`) is suppressed for sentinels so the code stays clean.
- **Currency has no default**: empty or unknown after edge normalization is `requisition_currency_invalid` (400); normalization happens at the gateway *and* the service api (idempotent, defense in depth).
- **Read endpoints are out of scope** (PRD §15 lists only `POST /api/v1/requisitions` and `POST /api/v1/requisitions/{id}/submit`; the issue says nothing about reads) — but the store's `Get` exists because the ownership check needs it.
- Dev note filename follows the repo's zero-padded convention (`029-…`), matching the plan's artifact list.

## Follow-ups

- **Pre-existing test leak found (not fixed here — unrelated to #29 per AGENTS.md rule 2):** in `services/procurement/server/api_test.go`, every `startProcurement`-based test closes the pool via `defer cleanup()` *before* its `t.Cleanup` row-deletion runs, so the deletion fails silently and seed rows (`G-01`, `L27-*`, and now `PR-*`) leak on every run. `TestVendorGRPCList` (from #27) has no pre-clean, so it fails with `vendor_duplicate_code` whenever `go test` runs twice against the same database (verified on a local PostgreSQL 17; CI is unaffected because each job gets a fresh database). Fix shape: pre-clean at test start (as the lifecycle tests already do) or close the pool in `t.Cleanup` instead of a defer. The requisition tests added here pre-clean, so they tolerate leftovers.
- Read endpoints (get/list/timeline) are separate issues; the replay contract above is already written for the post-approval world.
- #45 outbox: `PullEvents()` is still unpersisted — submit/create events live only in memory today.
- Item ordering is `ORDER BY created_at, id`; if the UI ever needs stable client-defined order, an `item_order` column is a small migration.
- `go test -race` remains unrunnable locally (no gcc/cgo); worth adding to CI if it isn't already.
- Vendor's `ErrIDInvalid` is still never raised in procurement (pre-existing, untouched).
